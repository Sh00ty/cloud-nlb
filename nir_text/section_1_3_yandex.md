### 1.3 Yandex Cloud L3/L4 Load Balancer

Ещё одним примером промышленной реализации L3/L4 балансировщика нагрузки является решение, разработанное в Яндекс Облаке [7]. Яндекс опубликовал достаточно подробное описание архитектуры, что нетипично для крупного провайдера и позволяет провести содержательный анализ.

В плоскости данных Яндекс применяет VPP (Vector Packet Processing) для высокопроизводительной обработки пакетов [8]. Управляющая плоскость декомпозирована на несколько компонентов, а именно распределённое хранилище для хранения состояния системы, управляющую службу для конфигурации и размещения виртуальных адресов и отдельный сервис проверок состояния узлов обработки.

Сервис проверок разделён на управляющий API и исполнительные узлы, непосредственно опрашивающие серверы. Такое разделение позволяет масштабировать исполнительный слой независимо от управляющей плоскости. При росте числа проверяемых серверов добавляются исполнительные узлы, тогда как управляющий API остаётся единым для всей системы. Выход из строя одного компонента не приводит к полной недоступности балансировщика, а ограничивается деградацией отдельных функций.

Детали внутреннего устройства кластера проверок в публикации не раскрыты. Нет описания того, как шардируются проверки между исполнительными узлами, как обнаруживаются отказы этих узлов и как перераспределяются проверки при изменении состава кластера. Без решения этих задач исполнительные узлы проверок образуют единую точку отказа.

Как и другие решения в данной области, система Яндекс Облака является проприетарной и привязана к инфраструктуре провайдера. Публикация подтверждает тезис о том, что многие действительно крупные облачные провайдеры строят собственный балансировщик, аналоги которого в открытом доступе отсутствуют.
